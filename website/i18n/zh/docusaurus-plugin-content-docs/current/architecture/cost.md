# 一次投递和一次发布的开销

## 设备变体

PUBLISH 从套接字读入 Broker 的[内存](../components/broker/memory.md)中的一个接收缓冲区，长度恰好等于固定报头所声明的长度。
投递持有这个缓冲区，并从中借用主题和载荷，因此载荷在套接字和处理器之间不会被复制。
报文的报头被解析进投递；处理器结算或丢弃投递后，缓冲区回到 Broker。
一个报文若到达多个订阅，则从第二个订阅起，每个订阅各复制一次，放入它自己的接收缓冲区。

一次发布被编码进两个发送缓冲区之一，由 runner 写出。
发布者借出字节，`Ok` 表示报文已经进入会话。
确认是固定大小队列中的一条命令，由 runner 发送报文。

无论在启动时还是每条消息上，都不分配内存：每个缓冲区都是开发板声明的 `MqttState` 的一部分，其大小为 `(MESSAGES + 2) * PACKET` 字节，再加上每个订阅的少量空间。

## 堆变体

rust-mqtt 0.6 客户端为收到的每个字段分配自己的堆缓冲区，因此一次投递为每个字段占用一个堆缓冲区：主题、载荷和每个字符串属性。
缓冲区不经复制地移入消息，消息被丢弃时释放。

一次发布把消息的字节复制到一个暂存槽位。
槽位的缓冲区保留容量，因此槽位容纳过服务发送的最大消息之后，发布不再分配内存。
发布者借出字节，`Ok` 表示报文已经进入会话。

确认是固定大小队列中的一条命令。
它不分配内存，由 runner 发送报文。

所有队列在启动时就固定下来：32 条命令、8 个暂存槽位，以及每个订阅 16 条投递。

在 compio 上，网络为每次读取增加一次复制：`io_uring` 读入它自己持有的缓冲区，客户端再从中读取。

## 实测

仓库中的代码开销基准统计一条消息给运行它的核心带来的开销：用 callgrind 统计指令数，用 DHAT 统计分配次数，均为启用 fat LTO 的 release 构建，取对 mosquitto 运行 500 条与 1000 条消息之差。
测量时，设备变体运行在主机上，其应用和 runner 在同一个线程上驱动。

| 一条消息的开销 | 设备变体 | compio 上的堆变体 | `ruststream-rumqttc` |
|---|---|---|---|
| `QoS` 1 的一次投递，已确认 | 6,866 条指令，0 次分配 | 10,210 条指令，2.18 次分配 | 8,937 条指令，1.15 次分配 |
| 一次发布（一次回复的开销减去一次投递的开销） | 4,297 条指令，0 次分配 | 12,085 条指令，0.29 次分配 | 8,832 条指令，6.06 次分配 |

设备服务读取并回复原始字节，而另外两个服务解码并编码 JSON 消息体，所以设备服务的指令数不含编解码器的开销。
`just bench-code` 测量堆变体，`just bench-code-noalloc` 测量设备变体。
